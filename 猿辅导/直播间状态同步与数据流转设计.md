# 直播间状态同步与数据流转设计

> 结合 `tutor-box-cocos-hall` 状态同步框架与 `tutor-box-app-19702` 拖拽题业务代码整理。
>
> 这篇笔记重点回答：老师的操作如何到达学生端、ACK 到底是什么、消息如何尽量不丢、Header / Body / ActionWidget 为什么要分层、学生重进后如何恢复，以及拖拽吸附为什么不会因为网络延迟先飞回再闪回。

## 1. 先建立整体认知：直播同步不是“发一个 WebSocket 消息”

从老师操作到学生 UI 更新，可以抽象为下面这条链路：

```text
老师 Web/H5/Cocos 业务代码
        ↓
状态同步框架（Header / Body / ActionWidget）
        ↓
JSBridge
        ↓
老师端 Native
        ↓
长连接 / WebSocket
        ↓
接入网关
        ↓
消息服务 / 直播中台
        ↓
Room（房间路由、成员管理、状态保存）
        ├── 回传老师端：作为业务确认
        └── 广播学生端：驱动学生 UI 更新
```

学生端收到消息后的链路大致相反：

```text
Room → 消息服务 → 网关 → WebSocket → Native → JSBridge
     → Web/H5/Cocos 状态同步框架 → State → Render → UI
```

代码仓库主要能证实 Web/Cocos 状态层及它与外部通信层之间的契约。网关、消息服务、中台和 Room 的具体实现不在当前两个仓库中，因此面试时应当明确表达：

- 已知前端发送的数据结构、`syncId` 和回传处理方式；
- 已知 ActionWidget 能收到状态恢复数据；
- 可以根据现象推断服务端具有转发、广播和状态保存能力；
- 不能仅凭前端代码断言服务端的落库介质、重试次数、ACK 协议、消息队列或副本机制。

## 2. 三种消息解决的是三类不同问题

项目将同步数据分成 Header、Body 和 ActionWidget，不是单纯按数据格式分类，而是按生命周期、重要程度和恢复要求分类。

### 2.1 Header：一次实时动作的边界或意图

Header 用来描述“开始做什么”或“完成了什么动作”，本身通常不是需要长期保存的最终业务状态。

例如拖拽题中的：

```ts
@Core.Create.header()
readonly dragOrDrop: number[] = []
```

- `[from, item]`：开始拖拽；
- `[from, item, to]`：松手，准备放入目标区；
- Header 到来后可以打开一段 Body 实时流；
- 退出重进时，旧 Header 一般没有恢复价值。

弹幕也可以按照类似思路设计成瞬时消息：只需要在线用户在当下看到，历史弹幕不一定参与房间状态恢复。但是否直接使用该项目的 Header，还要看弹幕业务是否需要独立通道、历史回看和审核等能力。

### 2.2 Body：动作过程中的高频连续数据

Body 表示 Header 所开启动作过程中的连续数据，例如：

- 拖拽过程中的 `x/y`；
- 画笔轨迹点；
- 滚动条移动位置；
- 激光笔或鼠标位置。

拖拽题中：

```ts
@Core.Create.body()
readonly x = 0

@Core.Create.body()
readonly y = 0
```

Body 的目标是流畅和低延迟，而不是逐条永久保存。它允许节流、合并，甚至允许丢掉部分中间点，只要最新位置能够继续驱动动画。

在 `BaseStateStore` 中可以看到 Body 流由 Header 建立，并通过 `takeUntil(this.selfActionWidget$)` 在本端 ActionWidget 到来时结束。也就是说，ActionWidget不仅是最终状态，还充当了一次实时交互的收口点。

当前框架中的 Body 节流发生在前端状态同步层。服务端是否还有额外限流或合并策略，不能从当前仓库确认。

### 2.3 ActionWidget：关键、可恢复的最终状态

ActionWidget 保存的是业务关键节点，例如：

- 拖拽完成后，各吸附区里有哪些元素；
- 最终滚动位置；
- 作答结果；
- 当前课件页或关键互动进度。

拖拽题中：

```ts
@Core.Create.actionWidget()
dropContents: number[][]
```

它表达的是最终状态，而不是拖拽动画过程：

```text
dropContents[0] = [1, 3]
```

可以理解为第 0 个吸附区当前包含编号 1 和 3 的拖拽物。

ActionWidget 的核心价值是：

1. 它是一次交互的权威结果；
2. 它可以供迟到或重进的学生恢复 UI；
3. 发送方可以等待携带相同 `syncId` 的服务端回传；
4. 它可以终止 Header + Body 构成的临时实时流。

项目 README 也用滚动条举例：按下是 Header，滚动过程是 Body，最终位置是 ActionWidget。

## 3. ACK 到底是什么

ACK 是 acknowledgment，即“确认收到”。但在这个项目里，要区分两层含义。

### 3.1 传输层 ACK

TCP / WebSocket 底层能够确认字节是否到达对端传输栈，但这并不等于：

- 业务服务已经处理；
- Room 已经保存状态；
- 学生已经收到；
- 学生 UI 已经渲染。

因此，单靠 WebSocket 连接正常不能完成业务可靠性保证。

### 3.2 业务层 ACK

前端发送 ActionWidget 时生成唯一递增的 `syncId`，同时创建一个等待中的 Promise：

```text
发送 { scriptId, syncId, data }
             ↓
syncStateMap[syncId] = Promise resolver
```

服务端处理后把带有该 `syncId` 的事件回传给发送端。发送端收到后执行 `resolveSyncStateMap(syncId)`，对应 Promise 才完成。

因此，这套实现里的“ACK”更准确地说是：

> 服务端回传同一个 ActionWidget 业务事件，前端以相同 `syncId` 将它识别为本次提交的业务确认。

核心代码位于：

- `packages/hall-lib/src/core/stateSyncStream/globalStream.ts` 的 `sendWidgetData()`；
- 同文件的 `resolveSyncStateMap()`；
- `packages/hall-lib/src/appStore.ts` 对 ActionWidget 回传事件的处理。

### 3.3 ACK 能证明什么，不能证明什么

收到老师端 ACK 至少说明服务端链路对该消息进行了回传处理，但它不天然等于“所有学生都已成功渲染”。如果产品要求确认每个学生都收到，还需要学生回执、成员确认表或服务端投递状态，这会显著增加流量和复杂度。

直播教学更常见的做法是：

- 发送端通过业务 ACK 确认关键状态已被服务端接收；
- 在线学生通过广播实时更新；
- 漏消息或重连的学生通过 seq 补偿或最新快照恢复；
- 最终以服务端权威状态收敛，而不是要求每条 Body 消息都端到端确认。

## 4. 如何保证消息“不丢”

严格意义上的“绝不丢失”很难只靠某一个机制完成。通用方案是 ACK、超时重试、唯一 ID、顺序号、幂等、补偿和快照共同组成闭环。

### 4.1 发送端：ACK + 超时 + 重试

通用设计：

```text
生成 messageId / syncId
        ↓
发送并进入 pending
        ↓
在超时时间内收到 ACK？
   ├── 是：删除 pending
   └── 否：按退避策略重试
```

重试必须复用原来的消息 ID，不能每次生成新 ID，否则服务端无法判断它是重试还是新操作。

建议采用：

- 首次快速重试，随后指数退避；
- 设置最大次数或总超时时间；
- 离线后暂停立即重试，等待重连；
- pending 队列在刷新或进程重启后是否持久化，按业务重要性决定；
- 达到上限后提示用户“同步失败，请重试”，而不是无限等待。

需要注意：当前看到的 Web 框架代码明确存在 `syncId + Promise + 回传 resolve`，但没有据此确认一套完整的自动超时重试实现。因此面试时不能把“通用上应该有的重试”说成“这个仓库已经实现”。

### 4.2 服务端：幂等

重试会导致同一条消息到达多次，因此服务端要基于以下键做幂等：

```text
roomId + senderId + messageId(syncId)
```

相同键重复到达时：

- 不重复执行业务副作用；
- 可以再次返回原 ACK；
- 可以再次返回已保存的处理结果。

这样才能做到“至少一次投递 + 幂等处理”，最终获得接近业务上“恰好一次”的效果。

### 4.3 接收端：seq + 去重 + 缺口检测

服务端可以为房间消息分配单调递增的 `seq`：

```text
101 → 102 → 103 → 104
```

学生端维护 `lastSeq`：

- 收到 `seq <= lastSeq`：重复或旧消息，忽略；
- 收到 `seq == lastSeq + 1`：正常消费；
- 收到 `seq > lastSeq + 1`：发现缺口，请求补发或直接拉快照。

`syncId` 和 `seq` 解决的问题不同：

- `syncId/messageId`：识别某次发送、匹配 ACK、实现幂等；
- `seq`：表达 Room 内消息顺序，发现接收端缺失。

### 4.4 重连：增量补偿或快照恢复

学生断线重连时，可以携带自己的 `lastSeq`：

```text
reconnect(roomId, lastSeq)
```

服务端判断：

- 缺口较小且历史仍在：补发 `lastSeq + 1 ... currentSeq`；
- 缺口过大或历史已淘汰：返回最新快照和快照对应的 `snapshotSeq`；
- 客户端应用快照后，再消费 `snapshotSeq` 之后的增量消息。

这能避免“拉快照过程中又产生新消息”导致覆盖新状态。

## 5. 学生晚进教室时会看到什么

### 5.1 只发生过 Header

如果老师只发送了 Header，之后没有形成 ActionWidget，学生在 Header 之后才进入：

- 旧 Header 通常没有必要重放；
- 学生不会为了历史动作重新播放一次拖拽开始动画；
- 如果进入时动作仍在进行，是否同步当前临时过程取决于 Room 的实时流保留策略；当前前端仓库无法确认服务端是否缓存 Header/Body。

这正是 Header 不适合承载最终业务结果的原因。

### 5.2 已经产生 ActionWidget

如果老师完成拖拽并生成了 `dropContents`：

- 学生实时在线时通过广播更新；
- 学生稍后进入或退出重进时，通过 ActionWidget 状态恢复；
- UI 直接呈现最终吸附结果，不必重新播放老师过去的整段拖拽轨迹。

ActionWidget 不应简单理解为“把所有历史 ActionWidget 从头播放一遍”。更准确的理解是：框架具备 ActionWidget 事件和状态恢复能力，具体是重放事件还是合并后的最新状态，取决于 Manager 的合并策略和业务的 `needReplay` 配置。对拖拽题这种状态型交互，恢复目标是得到当前 `dropContents`，而不是复现每一次历史手势。

## 6. 拖拽题的完整数据流转

以“老师把拖拽物 A 放到吸附区 A”为例。

### 6.1 按下：Header

老师按住拖拽物时：

```ts
this.stateStore.setState({
  dragOrDrop: [dragSource.parentIndex, dragSource.childIndex]
})
```

学生收到后建立对应的拖拽上下文，找到正在被拖动的元素。

### 6.2 移动：Body

老师移动手指或鼠标时持续更新：

```ts
this.stateStore.setState({ x, y })
```

学生端用最新坐标调用 `seekTo(x, y)`，显示拖拽物跟随移动。中间个别位置丢失通常不会破坏最终结果，所以 Body 可以节流。

### 6.3 松手：Header

老师松手时发送：

```ts
this.stateStore.setState({
  dragOrDrop: [fromIndex, itemIndex, targetIndex]
})
```

这里需要修正一个容易混淆的理解：

> “松手/放到哪个区”的动作命令是 Header；动作完成后得到的 `dropContents` 最终状态才是 ActionWidget。

### 6.4 本地先完成吸附

`dragOrDrop` 的 render 会调用 `dragDropComplete()`，正常情况下进一步执行：

```ts
dropTarget.fillChildren(tempDragingItem, seek)
```

`fillChildren()` 会把节点移动到目标位置，并在 `DragSource.fill()` 中更新：

```ts
this.parentIndex = dropTargetIndex
this.childIndex = targetIndex
```

因此老师端是先乐观更新 Cocos 节点，而不是让节点停在半空中等待 ActionWidget 回传。

### 6.5 提交最终 ActionWidget

本地吸附处理完成后，代码更新最终状态：

```ts
this.newDropContents = newDropContents
this.stateStore.setState({
  dropContents: this.newDropContents.concat()
})
```

框架为该 ActionWidget 生成 `syncId`，发送到服务端，并等待同一 `syncId` 的事件回传。

### 6.6 服务端广播，学生应用状态

在线学生收到 `dropContents` 后执行 `dropContentChanged()`：

1. 清理各吸附区当前子元素；
2. 根据新的 `dropContents` 重新建立归属；
3. 使用 `seek=true` 直接设置坐标；
4. 不重新播放完整拖拽动画。

老师端收到相同 ActionWidget 后也执行一次权威状态校准，同时相应 `syncId` Promise 完成。

## 7. 网络不好时，为什么正确吸附不会先飞回再闪回

核心原因不是“网络绝对不会丢包”，而是 UI 更新顺序经过了设计：

```text
本地松手
  ↓
乐观执行 fillChildren，节点先吸附
  ↓
发送最终 dropContents
  ↓            网络延迟期间节点保持在吸附区
服务端回传
  ↓
使用 seek=true 按权威状态静默校准
```

具体有三层保障：

1. **节点已被本地直接移动。** `fillChildren()` 在 ActionWidget 确认前已经执行。
2. **节点归属已经修改。** `parentIndex` 已经变成目标吸附区，不再被当成自由元素重置。
3. **回传校准不播放动画。** `dropContentChanged()` 清理并重填时使用 `seek=true`，操作在同一次同步 JS 调用内完成，通常不会渲染出中间回原点的一帧。

所以这是一种“本地乐观 UI + 服务端权威状态确认”的设计。

### 7.1 哪些情况仍然会回退

不能把它表述成任何情况下都不会回退：

- 如果业务判断答案错误，代码会执行 `notMatch()`，随后 `notFill()`，这是产品设计的错误反馈；
- 如果目标区域已满或不允许吸附，也可能返回原位；
- 如果服务端权威状态和本地乐观结果不一致，客户端应该服从服务端状态，因此可能发生纠正；
- 如果 ActionWidget 永久未确认，UI 可能暂时仍显示本地吸附，但该状态尚未成为可恢复的权威状态，需要超时提示或重试机制兜底。

错误答案分支不会提交这次新的 `dropContents`，因此“错误后飞回”不是网络闪回，而是明确的业务逻辑。

## 8. 为什么不把所有数据都做成 ActionWidget

如果每个拖拽坐标都作为 ActionWidget：

- 服务端需要保存大量没有恢复价值的中间点；
- 每个点都参与 ACK 和合并，延迟、流量、内存都会增加；
- 学生重进时可能重放大量过期动画；
- 高频状态更容易形成排队和反压。

如果所有数据都只做 Header/Body：

- 学生中途进入无法知道最终结果；
- 断线后无法恢复；
- 最后一条松手消息丢失时 UI 可能永远停在错误状态。

因此三层模型本质上是在平衡：

| 类型 | 关注点 | 是否高频 | 是否要求恢复 | 示例 |
| --- | --- | ---: | ---: | --- |
| Header | 动作边界、意图 | 低 | 通常不需要 | 按下、松手、开始滚动 |
| Body | 实时过程、流畅度 | 高 | 通常不需要 | x/y、轨迹、滚动过程 |
| ActionWidget | 关键结果、一致性 | 低 | 需要 | dropContents、最终页码、作答结果 |

## 9. 一套更完整的直播同步通用方案

如果从系统设计角度补全整套可靠性，可以这样描述：

### 发送侧

- 业务消息生成唯一 `messageId/syncId`；
- 关键状态进入 pending 队列；
- 收到业务 ACK 后移除；
- 超时执行有上限的指数退避重试；
- 重试复用原 ID。

### Room / 服务端

- 校验用户是否有操作权限；
- 按 `roomId + senderId + messageId` 幂等；
- 为房间事件分配单调 `seq`；
- 更新房间权威状态或快照；
- 向发送端回 ACK；
- 向在线学生广播。

### 接收侧

- 按 messageId 去重；
- 按 seq 排序并发现缺口；
- Header/Body 驱动实时动画；
- ActionWidget 更新权威业务状态；
- UI render 保证重复应用同一状态结果一致。

### 重连侧

- 携带 `lastSeq` 重进 Room；
- 缺口较小时补增量；
- 缺口较大时拉快照；
- 快照带 `snapshotSeq`；
- 应用快照后继续消费后续增量。

最终保证的不是“每个网络包只出现一次”，而是：

> 网络允许重复、延迟、乱序和短暂丢失，但业务通过重试、幂等、顺序校验和快照恢复，最终收敛到一致状态。

## 10. 面试时可以直接使用的回答

> 我们把直播互动数据分成 Header、Body 和 ActionWidget。Header 表达一次动作的开始或结束，例如拖拽按下、松手；Body 表达过程中高频但允许合并的数据，例如 x/y；ActionWidget 表达需要可靠保存和重进恢复的最终状态，例如各吸附区的 dropContents。
>
> 关键状态发送时会带 syncId，并在前端建立 Promise。服务端把处理后的同一事件回传，前端根据 syncId resolve，这相当于业务 ACK。在线学生通过广播实时更新，迟到或重连学生通过 ActionWidget 状态恢复。更完整的可靠性还需要服务端幂等、房间 seq、缺口补偿和快照；这些服务端实现细节不在当前前端仓库里，我只能确认双方的契约，不能虚构具体存储和重试策略。
>
> 拖拽题还做了本地乐观更新：老师松手后，Header 先触发 dragDropComplete，本地直接 fillChildren，把节点放进吸附区并修改 parentIndex；然后才提交最终 dropContents。服务端回传后用 seek 模式无动画校准，所以网络慢只会延迟确认，正常情况下不会先飞回原点再闪回。错误答案执行 notMatch 和 notFill 则是业务回退，不属于网络闪回。

1. Header 管动作边界，Body 管实时过程，ActionWidget 管最终可恢复状态。
2. `syncId` 解决发送确认和幂等标识，`seq` 解决房间消息顺序与缺口检测。
3. 学生端可靠性不能只靠广播，还需要重连补偿或快照恢复。
