## AI报障处理

### 项目简介

AI 自动分析线上报障的 Agent 工具，核心目标是减少工程师在重复性故障排查上的人力消耗，降低 MTTR（平均故障响应时间）。

**两条触发路径：**

- **定时触发**：定时任务批量扫描所有线上报障，从知识库中召回相似历史 case，结合代码上下文完成自动推断，输出处置建议。适用于非紧急报障的后台消化。
- **手动触发**：工程师手动触发单条报障的查询分析流程，适用于需要快速响应的紧急故障。

**核心技术栈：**

- **NestJS**：主服务，承载定时触发、手动触发、置信度路由、Claude Code SDK 调用的全部编排逻辑
- **PostgreSQL + pgvector**：向量数据库，存储历史报障的 embedding，支持语义相似度召回
- **Claude Code SDK**：以 Agent 模式分析代码，自主读取相关文件和 git 历史，构建代码上下文

---

### 架构

```
定时器（NestJS @Cron）/ 手动触发（HTTP 接口）
                ↓
        NestJS 编排层
                ↓
       pgvector 向量召回（Top-K 相似 case）
                ↓
         LLM 评估置信度
       ┌─────────┴─────────┐
    高置信度             低置信度
       │                   │
  返回 RAG 结论    Claude Code SDK
       │           Agent 深度排查
       │         ┌─────────┴──────────┐
       │      有结论               无结论
       │         │                   │
       └──→ 输出处置结论       降级：输出可疑方向
                 │
       工程师确认 → 写回 pgvector 知识库
                 ↑______________________↓
                        知识飞轮闭环
```

**核心设计思想：成本递进的分级处理**

- **第一级（较低成本）**：pgvector 召回 + 轻量 LLM 置信度评估，高置信度直接复用历史结论
- **第二级（较贵）**：置信度不足时才触发 Claude Code SDK，拉代码做深度分析，成本高但精准
- **第三级（兜底）**：SDK 也无法定位根因时，降级为参考提示，不输出确定性结论，避免误导研发

全部逻辑在 NestJS 内部流转，没有外部编排平台依赖，链路清晰，调试和异常处理统一。

### 项目亮点（面试重点）

#### 1. 置信度分层 × 成本递进处理

置信度不只是输出端的路由标签，而是驱动整条处理链路升降级的核心信号。

**三级处理逻辑：**

| 级别 | 触发条件 | 处理方式 | 成本 |
|------|----------|----------|------|
| 高置信度 | RAG 召回到高度相似的历史 case，模型判断可直接复用 | 直接输出历史结论，推送给值班工程师 | 最低（仅 RAG + 轻量 LLM 判断） |
| 低置信度 | 召回相似度不足，或模型对推断结果不确定 | 触发 Claude Code SDK，拉取代码仓库做 Agent 深度排查 | 较高（SDK 调用 + 代码分析） |
| 无结论 | SDK 深度排查后仍无法定位根因 | 降级处理：输出分析过程中的参考信息和可疑方向，不给出确定性结论 | 已产生，做好兜底 |

**为什么这样设计而不是全部走深度分析：**
绝大多数线上报障是重复出现的已知问题，高置信度路径能覆盖大多数 case 且速度最快。只有真正的"新问题"或"疑难 case"才需要 SDK 介入，这样整体的 token 成本和响应延迟都控制在合理范围内。

**第三级降级的价值：** 与其输出一个错误的结论误导研发，不如诚实地说"我没排查出来，但这些是可疑方向"——这体现了对 AI 局限性的清醒认知，也是系统可信度的保障。

**面试引导**：可以这样说——"我们没有用简单的置信度阈值做静态路由，而是把置信度设计成触发不同处理链路的动态信号，高置信度复用历史结论节省成本，低置信度升级到代码深度分析，还有兜底的降级策略，整个系统在准确性和成本之间做了分层的权衡。"

---

#### 2. 知识飞轮（Knowledge Flywheel）

当前大多数 Agent 工具是单向消费知识库的，本项目设计了反馈闭环：

1. AI 分析报障 → 给出推断结论
2. 工程师确认结论正确（或修正）
3. 确认过的链路（报障描述 + 根因 + 处置方案）**自动写回知识库**
4. 下次遇到相似问题，召回质量更高，推断更准确

随着时间积累，系统越用越准，形成正向飞轮。这是让项目具备长期价值的核心机制。

**面试引导**：可以问面试官"你们现有的知识库是怎么维护的？"——大多数公司靠人工整理，对比之下飞轮机制的价值一目了然。

---

#### 3. Workflow 可观测性

整条分析链路经过多个节点，每个节点都要打日志埋点，否则出问题无从定位：

- **召回阶段**：记录 pgvector 返回的 Top-K 相似度分数，分数普遍低说明知识库积累不足
- **置信度评估**：记录每次 LLM 给出的置信度值和最终走了哪条分支，统计各分支的触发比例
- **SDK 排查阶段**：记录 Agent 循环轮次、工具调用次数、总耗时和 token 消耗
- **整体链路**：从报障进入到结论输出的端到端耗时，按来源（cache/rag/sdk/fallback）分别统计

有了这些数据，可以回答"召回质量够不够好"、"SDK 触发是否过于频繁（成本是否可控）"、"AI 推断准确率是多少"等关键问题。

**面试引导**：可观测性是工程化成熟度的体现，面试时提这个能说明你不只是"跑通了 demo"，而是考虑了生产环境的长期运营。纯代码实现的另一个好处是：每个节点的日志、耗时、异常都统一走 NestJS 的 Logger，不需要在多个系统间来回查。

---

#### 4. Claude Code SDK 自主控制代码上下文

这是本项目与普通 RAG 系统最本质的区别，也是最深的技术亮点。

**普通 RAG 的做法**：把代码切片 → 向量化 → 相似度检索 → 把检索到的片段塞进 prompt。问题是：代码不是孤立的文本，函数 A 调用函数 B，静态切片会丢失调用链语义。

**本项目的做法**：Claude Code SDK 是 Agent，它拥有工具调用能力（读文件、执行 bash、grep 搜索、git 命令），工作流如下：

1. 接收报障描述作为起点
2. **AI 自己决定**先搜索什么关键词（错误信息、类名、函数名）
3. 找到相关文件后读入，发现调用了另一个模块，**自动顺着调用链继续读**
4. 执行 `git log --grep` 或 `git blame`，定位该代码段最近的变更时间和作者
5. 上下文是 AI **动态构建**的，而非预先确定的

这意味着 AI 能真正"理解"报障的代码上下文，而不只是做文本匹配。Claude Code SDK 自主控制 context 的范围，也天然规避了大仓库 context 超限的问题——它只读它认为相关的部分。

**面试引导**：可以这样说——"我们没有用传统的代码 RAG，而是利用 Claude Code SDK 的 Agent 能力，让 AI 像工程师一样去'查代码'，自己决定读哪些文件、查哪些提交记录，这样拿到的上下文质量比向量检索高得多。"

### 选型原因与技术路线设计

#### 为什么选择纯代码编排而不用 Dify？

**选型对比：**

| 方案 | 适用场景 | 问题 |
|------|----------|------|
| Dify | 快速验证、RAG 原型 | 低置信度时需回调 NestJS，链路变成 NestJS→Dify→NestJS，绕路且多一层故障点 |
| LangChain / LlamaIndex | 复杂多 Agent 协作 | 引入大量胶水代码，对 NestJS 项目侵入性强 |
| NestJS 纯代码编排 | 生产系统 | 逻辑完全自主，调试统一，异常处理清晰 |

**选纯代码编排的核心理由**：本项目的核心逻辑——RAG 召回 → 置信度路由 → SDK 调用——本质上是一个**有条件分支的串行流程**，并不需要可视化编排平台。用 NestJS 直接实现，链路清晰，日志统一，所有节点的耗时、错误都在同一个服务里可观测。引入 Dify 反而会增加系统复杂度和运维成本。

---

#### 为什么用 Claude Code SDK 而不是普通代码 RAG？

**选型对比：**

| 方案 | 问题 |
|------|------|
| 代码向量化 RAG | 代码切片后丢失调用链语义，跨文件依赖无法感知，检索结果是碎片 |
| 静态分析工具（AST 解析等） | 只能理解结构，无法结合报障语义做推断，需要大量定制开发 |
| Claude Code SDK（Agent 模式） | AI 自主决定读什么，能顺着调用链读，能查 git 历史，上下文质量最高 |

**选 Claude Code SDK 的核心理由**：故障排查本质上是**动态的信息收集过程**——工程师排查时不会预先知道要看哪些文件，而是顺着线索一步步找。Claude Code SDK 复刻了这个过程，让 AI 像工程师一样查代码，而不是做静态的文本匹配。

---

#### 为什么设计两条触发路径而不是统一？

**核心矛盾**：批量扫描和紧急响应的优先级、资源占用完全不同。

- 定时触发是**低优先级后台任务**，可以慢慢跑，不能影响线上主链路
- 手动触发是**高优先级实时任务**，要求秒级响应，容不得排队

如果合并成一条路径，要么紧急报障被批量任务堵住，要么批量任务抢占资源导致成本暴增。两条路径分开，可以独立控制并发限制、资源配额和超时策略，互不干扰。

---

#### 整体技术路线的设计逻辑

```
报障输入（定时 @Cron / 手动 HTTP 接口）
                ↓
        NestJS BugAnalysisService
                ↓
       ① pgvector 向量召回（Top-K 相似 case）
                ↓
       ② LLM 置信度评估（claude-haiku，低成本）
          ┌────────┴──────────┐
        ≥0.8                 <0.8
          │                   ↓
     返回 RAG 结论  ③ Claude Code SDK
          │         Agent 循环（读文件/git/grep）
          │         ┌──────────┴──────────┐
          │      有结论（≥0.5）        无结论（<0.5）
          │         │                   │
          └─────────┴──→ 返回结论    降级：返回可疑方向
                         │
             工程师确认 → 写回 pgvector
                         ↑_________________↓
                              知识飞轮
```

**设计逻辑**：
- **NestJS** 是唯一的编排层，三个处理阶段全在一个服务内流转，无跨系统调用
- **置信度** 驱动链路升降级：高置信度止步于 RAG，低置信度才升级到 SDK，控制整体成本
- **claude-haiku** 做置信度评估（便宜快），**claude-opus** 做 SDK 深度排查（贵但精准），模型分级使用
- **知识飞轮** 让系统越用越准：SDK 排查出的新结论写回 pgvector，下次相同问题走 RAG 高置信度路径
