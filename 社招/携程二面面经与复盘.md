## 一、先说结论

这场二面的重点不是前端八股，而是考察三个方面：**项目是否由你真正主导、方案能否经得住指标和实现细节追问、做出的工具能否实际落地和推广**。

整体表现可以概括为：

- **优势**：项目覆盖微前端、Hybrid、B 端性能优化、AI 报障和设计稿转代码，方向丰富；能给出包体积下降 30%+、切换时间下降 50%+、值班耗时由约一天降到 2～3 小时等结果。
- **主要问题**：不少答案先从实现细节说起，缺少背景、目标、口径、结果的完整闭环；对 Long Task 指标、React 渲染隔离、监控实现等问题回答不够准确。
- **项目主导性不足**：面试官多次追问使用人数、推广方式、是否强制、是否已跨组落地，说明他在判断项目到底是个人探索、组内工具，还是有组织影响力的正式项目。
- **AI 项目说服力一般**：能讲清工作流，但准确率、人工标注、Agent 迭代和业务流转机制没有形成强数据闭环。
- **面试官直接反馈**：技术深度“可能不是很够”。这是本场最重要的信号，后续应重点提升底层原理、指标定义和方案边界的表达。

### 1. 自我介绍与代表项目

面试官的问题：

1. 请做自我介绍。
2. 现在是否仍在猿辅导？
3. 介绍一个最能代表你能力、体现主导性和主动性的项目。

你的回答要点：

- 在猿辅导工作三年多，主要经历包括：
  - C 端伴读业务微前端：子应用体积下降 30%+，结合预加载使切换加载时间下降 50%+；
  - C 端 Hybrid 架构：发版周期从一周缩短到约两天一次；
  - AI 报障提效；
  - B 端性能优化：将主要长任务降到 90ms 内。
- 选择微前端项目作为最能代表能力的项目。
- 方案通过稳定模块 ID 和 Webpack Runtime 复用公共依赖，通过预加载降低切换耗时，使用 CSS-in-JS 降低样式冲突，并由基座提供生命周期和资源清理能力。

复盘：

- 自我介绍信息密度高，项目与数据齐全。
- “最有代表性的项目”应先强调为什么由你主导：你识别了什么问题、做了什么关键决策、推动了哪些团队、承担了什么风险，而不是马上进入 JS/CSS 隔离。
- “稳定模块 ID → 共享公共模块”的机制需要讲得更严谨，避免让人误以为仅靠稳定 ID 就能完成跨构建共享。应明确 Runtime、模块映射、版本约束和公共依赖由谁提供。
- CSS-in-JS 只能降低命名冲突，不能笼统等同于完整 CSS 隔离；全局样式、Reset、Portal 和第三方组件仍需治理。

推荐表达顺序：业务痛点 → 个人职责 → 约束与选型 → 核心实现 → 数据口径 → 项目结果 → 方案边界。

### 3. B 端流程图性能优化

面试官的问题：

1. 核心流程图节点的长任务耗时降低，具体做了什么？
2. 长任务耗时降低的指标口径是什么？
3. 除了 Chrome Performance 录制，还有其他衡量手段吗？
4. 性能监控是如何实现的？是接入 SDK，还是自己做的？
5. 渲染隔离和 React 默认调和是什么关系？
6. 为什么不用 Canvas 或虚拟列表？

你的回答要点：

- 先用 Chrome Performance 录制用户操作，发现流程图计算中有高时间复杂度算法；通过增加空间占用降低时间复杂度。
- 算法优化后仍有卡顿，继续发现 React 组件重复渲染，通过组件拆分和 `memo` 缓存减少重渲染。
- 最终录制中已没有明显长任务，主要任务降到 90ms 内。
- 使用 `PerformanceObserver` 采集 Long Task、FCP 等数据，结合路由和流程图 ID 上报到公司平台。
- 没有采用 Canvas，因为流程图包含大量文本，需要浏览器搜索和原生 DOM 能力；虚拟列表会导致未渲染内容无法全文搜索，且长表单需要快速滚动和全局跳转。

做得好的地方：

- 排查路径完整：录制 → 找算法热点 → 优化复杂度 → 再录制 → 找渲染热点 → 拆分与缓存 → 补监控。
- 对 Canvas/虚拟列表的选型回答结合了全文搜索、DOM 语义和业务交互，不只谈性能。

主要问题：

- **Long Task 的定义说错了**：标准 Long Tasks API 关注主线程持续时间超过 50ms 的任务，不是“每一帧是否在 90ms 内”。90ms 可以是你的优化目标，但不能当成浏览器长任务标准。
- 指标口径不完整：只说“录 30 秒、看 Performance”不足以证明优化效果。应固定设备、数据规模、操作脚本、冷热缓存，并比较优化前后的 P50/P95、最长任务、长任务数量、INP、FPS 或提交次数。
- `PerformanceObserver` 是采集入口，不应推测为“计算每一帧 JS 时间”。更准确的说法是观察 `longtask`、`paint` 等浏览器提供的 PerformanceEntry。
- 面试官问“渲染隔离和 React 默认调和的关系”时没有答出来。需要说明：组件拆分本身不会阻止父组件更新向下协调；`React.memo`、稳定 props、状态下沉、selector 订阅等才决定子树是否 bailout。缓存也需权衡比较成本与内存。
- “算法让 AI 优化了一版”会削弱个人贡献。应能说出原算法、复杂度、数据结构变化及正确性验证。

建议答案框架：

> 我们先固定一份 N 节点、E 条边的典型数据，用相同设备和操作脚本采集基线。火焰图显示布局/遍历算法是主要 JS 热点，原实现存在重复扫描，复杂度接近 O(N²)；我通过索引表缓存中间结果，把重复查找降为近似 O(1)，主计算降到 O(N+E)。第二轮分析发现剩余时间主要来自 React 重复协调和提交，于是将高频交互状态下沉，拆分节点子树，稳定回调与对象引用，并用 `memo` 让未变化节点 bailout。最后比较优化前后长任务数量、P95 任务耗时、INP 和 React commit 次数，并通过 `PerformanceObserver` 在线采集 `longtask`，关联路由、流程图 ID 和数据规模上报。

### 4. B 端互动题模拟器

面试官的问题：

1. 模拟器的主要作用是什么？
2. 它主要用于开发，还是也提供给其他用户？
3. 能否做到与真机 1:1？具体如何实现？
4. 原来用 WebView，模拟器中是否改成 iframe？

你的回答要点：

- 模拟器复刻 C 端互动题所依赖的端能力，使 WebApp 无需扫码、换包和真机调试即可在本地开发。
- 后续也提供给老师做内容预览。
- 在模拟器环境把原 JSBridge/协议调用转为 `postMessage` 与 iframe 外层通信。
- 在 WebApp 启动前代理 XHR 和 Fetch，把请求转到本地后端服务，模拟开始测验、提交、结束测验等状态流转。

复盘：

- 核心架构讲清楚了：真实环境是 Native + WebView，模拟环境是模拟器壳 + iframe；两者复用同一业务 WebApp。
- “1:1”不宜说得太满。模拟器通常只能保证协议和主流程一致，真实 WebView 内核、网络、权限、生命周期、弱网、系统返回键等仍需真机验证。
- 建议补充协议契约测试：同一份协议 Schema 驱动 Native 和模拟器实现，并对消息、错误码、时序和状态机跑一致性测试。

面试官的问题：

1. AI 报障如何工作？可以理解为 Agent 吗？

6. 准确结果是否由人工标记？
7. 是否会根据反馈持续更新 Agent？

你的回答要点：

- 平均每天十多条问题，由每周轮值的值班同学处理；高优问题当周修复，复杂或跨团队问题拆成正式任务，交给产品评优先级和后续排期。
- 原先每周约需一天处理，接入后约需 2～3 小时。
- 由值班同学标注诊断是否准确，统计一个月准确率；后续通过补充 PRD、测试用例和排障 Skill 改进上下文。

做得好的地方：

- 从数据拉取、上下文构建、代码分析、结果回填到人工 Review，工作流完整。
- 没有声称完全自动修复，保留人工确认，符合报障场景的风险控制。

主要问题：

- 没有给出实际准确率、覆盖率或节省工时的统计口径。只有“从一天降到两三个小时”但未说明样本周期、值班人数和问题复杂度。
- 面试官反复质疑人工流转，说明流程治理没有说服他。应说明状态机、SLA、责任人、超时提醒、转派和关闭条件，而不是只说“值班同学会处理”。
- “人工判断准确”需要更细的标签，如完全正确、定位正确但方案错误、上下文不足、误判，并衡量采纳率和平均定位时间。
- Agent 更新机制不能只依赖换模型或补知识库。应有失败样本集、离线评测、Prompt/Skill 版本、灰度对比和回归门槛。

建议补充的指标：诊断覆盖率、根因定位准确率、建议采纳率、误报率、人工平均排查时长、首次响应时间、问题闭环时长，以及按业务/问题类型拆分后的效果。

## 四、这场面试暴露出的核心问题

### 1. 指标口径不严谨

简历数字很多，但被问到如何测量时容易变成“Performance 录 30 秒看一下”“人工 Review 后统计”。以后每个数字都要准备六项：定义、采集方式、样本范围、基线、结果、局限。

### 2. 个人贡献与 AI 贡献边界模糊

“让 AI 优化一版”“通过 AI Review 代码”会让面试官继续追问你真正掌握了什么。表达时要讲清：AI 给了什么候选方案，你如何判断、修改、验证和承担结果。

### 3. 项目影响力有计划、缺结果

设计稿转代码项目当前主要是组内试用，却多次提到未来部门推广。回答应把事实分层：当前覆盖、试点数据、推广条件和下一阶段计划。

### 4. 底层原理回答不够确定

Long Task、`PerformanceObserver`、React 调和与 bailout 等问题不能靠现场推测。对不确定的细节，先承认边界，再回答确定部分，比连续使用“应该”“大概”更可靠。

### 5. 回答结构偏散

高频出现从细节切入、说到一半换方向的情况。项目题统一采用：

> 背景与目标 → 我的职责 → 关键约束 → 方案与取舍 → 实现细节 → 数据结果 → 风险和边界

7. 回忆并补记现场编码题，单独整理最初方案、复杂度、边界条件和未完成原因。

## 六、可直接复用的二面项目开场

> 我选 B 端流程图性能优化作为代表项目。这个项目最能体现我的问题定位和完整落地能力：内部用户反馈大流程图交互明显卡顿，我负责从性能基线、根因分析、算法和 React 渲染优化，一直到线上监控闭环。我们先用固定规模数据和统一操作脚本录制基线，通过火焰图定位到重复遍历算法和大范围组件重渲染两个主要瓶颈；随后用索引缓存降低重复查找，通过状态下沉、组件拆分和 memoization 缩小更新范围。最后用相同场景复测，并通过 PerformanceObserver 在线采集 Long Task，关联路由、流程图 ID 和数据规模上报。这个项目的难点不只是把一次录制变快，而是建立了后续可以持续发现退化的监控闭环。
