## 2. Webpack Runtime 与模块共享的解释不够准确

**对应时间：约 06:22–10:57**

### 原回答的问题

你的整体方向是对的：Webpack Runtime 负责模块注册、缓存、加载和异步 chunk 加载；打通主、子应用的模块解析上下文后，可以实现依赖共享。但以下口径有风险：

- 把 Webpack 默认 module id 描述为“随机数字，用于保证模块隔离”不够准确。module id 的生成取决于 Webpack 配置和优化策略，例如 `natural`、`named`、`deterministic`；其主要作用是标识编译产物中的模块，不应简单解释为随机隔离。
- “把 React 的 module id 固定成 react，子应用 resolve 到这个 id”描述得过于简化。真正需要说清的是共享模块的**注册表、作用域、版本协商、加载时机和 fallback 规则**。
- 没有说明自研机制与 Module Federation 的相似点和差异，容易让面试官怀疑只是重新实现了一个简化版模块联邦。

### 更好的回答结构

> 先说结论：普通 Webpack 构建中，每个 compilation 默认维护自己的模块表、缓存和 chunk 加载逻辑；我们做的改造，是让子应用在解析约定的公共依赖时，优先从基座提供的共享模块注册表取模块实例，其余依赖仍走子应用自己的模块表。这样 React、React DOM 和公共组件库不需要在每个子应用重复打包。实现上我们在构建阶段生成共享依赖清单，在运行时完成注册和查找，并对版本、加载顺序和缺失依赖设置校验或 fallback。它和 Module Federation 的目标相似，但我们的业务拓扑固定为单基座加载多个子应用，因此只保留了单向共享和生命周期管理，协议更轻。

这段回答会比围绕 module id 反复解释更完整，也更能体现架构设计能力。

## 3. 对 React 多版本共存风险的解释有技术偏差

**对应时间：约 09:42–10:57**

### 问题

你说某些包不能共存，是因为 React 会挂到 `window`、与全局方法共用后可能混乱。这个解释不准确：

- React 作为模块使用时通常不会因为加载就挂到 `window`。
- 多份 React 真正典型的风险包括 React 与 renderer 使用了不同实例导致 Invalid Hook Call、Context 身份不一致、公共组件跨运行时传递时行为异常，以及包体积增加。
- “JS 隔离就能隔离出来”也过于笼统。模块作用域隔离不等于浏览器运行环境隔离，DOM、事件、Storage、网络和全局对象仍然可能共享。

### 更好的说法

> 技术上可以让子应用保留自己的依赖版本：共享清单之外的模块走子应用私有模块表。但需要区分普通工具库和单例型依赖。像 lodash 这类库通常可以多版本共存；React、React DOM、路由上下文或状态容器如果会跨应用共享组件和上下文，最好声明为单例并做版本兼容校验，否则可能出现 Hook、Context 或 renderer 实例不一致。对于确实无法兼容的版本，我们会选择子应用完全自治，并禁止跨应用传递 React 组件实例，只通过序列化数据或事件通信。

## 5. 内存泄漏与快照兜底是本场最危险的回答

**对应时间：约 17:16–23:25**

### 问题

面试官对此进行了多轮追问，说明他没有被前面的回答说服。主要风险包括：

- “对 `window` 做快照，卸载时回滚，就能保证全局内存不泄漏”这个结论过强。
- 仅比较 `window` 属性无法发现通过 `addEventListener` 注册的监听器，因为事件监听列表不是普通可枚举属性。
- 快照也不能自动处理定时器、Observer、WebSocket、DOM 引用、闭包、第三方 SDK 和游离节点。
- 面试官提出“挂载后主应用自己新增监听器怎么办”时，你回答“记住来源”“可以存一下”，更像临场猜测，而不是项目中的真实机制。
- 关于样式，你顺着面试官说“删除 style 之后样式还生效”，技术上通常不成立：如果对应 `<style>` 元素或 stylesheet 被移除，其规则一般就不再参与样式计算。这里应该先澄清具体实现。

### 正确的回答策略

如果项目里真实做法没有覆盖这些细节，应坦诚区分“已实现”和“可以改进”：

> 我先修正一下，单纯对 `window` 属性做快照并不能覆盖事件监听器和所有内存泄漏。我们当时实际定位到的是子应用没有清理全局监听。业务侧首先修复卸载逻辑；基座兜底如果要可靠实现，需要在子应用执行上下文内代理 `addEventListener/removeEventListener`、定时器和 Observer 等资源创建接口，按子应用记录资源句柄，在卸载时定向清理。这样不是通过前后数量差判断，而是通过注册发生时的应用上下文判断归属。主应用新增的监听不会记到子应用资源表中，因此不会被误删。DOM 游离节点和闭包引用仍要结合 heap snapshot、allocation timeline 和生命周期测试排查，不能声称一个 window snapshot 能完全解决。

这类回答的关键不是表现得无所不知，而是**准确界定方案能解决什么、不能解决什么**。

- 面试官问缺点时，你回答“还好，只是需要学习”，没有体现架构权衡。实际成本可能包括 schema 演进、可选字段语义、调试可读性、生成代码体积、跨端版本错配和构建链复杂度。

### 更好的回答

> 我负责的是协议仓库设计、Web 侧 runtime 和接入规范。Proto 文件作为三端共同评审的唯一接口定义，通过 codegen 生成类型和序列化代码，减少方法名、参数和返回值在三端手工维护造成的不一致。Bridge 层还统一处理 request id、超时、错误码、版本声明和降级。选择 Protobuf 的核心原因是 schema 明确、跨语言代码生成成熟；二进制体积只是次要收益，而且要看 WebView 通道是否支持，否则可能仍需 Base64 或其他封装。代价是调试可读性和构建链复杂度增加，协议演进也必须遵守字段兼容规则。对于少量简单接口，JSON 更轻；当接口数量和跨端协作规模上升时，Protobuf 的收益才明显。

你的简历中其实已经写出了现场最应该使用的四个关键词：**TypeCode 路由、能力探测与降级、Native 网络代理、多版本兼容**。面试官问“你的主要产出”时，应按这四项展开，而不是只说“做了一个通用包、屏蔽了一些细节”。

可以补成：

> 我的个人产出主要有四块：统一三端接口定义和代码生成；用 TypeCode 做方法路由；在调用前做能力探测，对旧版本客户端提供降级；把鉴权和网络请求通过 Native 代理统一处理。这样 Web 业务可以独立发布，同时不会因为客户端版本差异直接调用不存在的能力。项目结果是研发投入降低约 60%，发布周期由 7 天缩短到 2 天。这里的投入和周期口径我会再说明具体统计范围。

## 8. AI 报障项目有亮点，但“60% 准确率”口径太模糊

**对应时间：约 32:00–38:45**

### 问题

- “准确率 60 多”没有定义：是根因命中率、建议可用率，还是值班同学采纳率？样本量多少？谁负责标注？
- 没有讲清数据安全、代码与日志权限、敏感信息脱敏等企业落地问题。
- 对模型幻觉的应对主要是“排查调用链、换更好的模型、沉淀 Skill”，不够系统。
- 缺少离线评测集、结构化输出、证据引用、工具结果校验、人工审批和回归评测等可靠性手段。

### 更好的回答

> 我们没有让模型直接修复上线，而是把它定位为值班排查助手。输入包括脱敏后的报障描述、关联日志、代码检索结果和产品文档，输出必须包含疑似根因、证据、置信度和建议排查步骤。我们用历史已关闭工单构建评测集，把“根因一级分类正确”和“给出可验证证据”作为主要指标；目前约六成案例能给值班同学提供有效方向，但这个数字仍受样本量和人工标注影响。线上保留人工复核，低置信度不自动给结论。提升可靠性的重点是优化检索上下文、限制工具权限、要求引用证据、做规则与测试校验，并对每次 Prompt、模型或工具变更跑回归评测，而不只是换更强模型。

简历写的是“每周排查线上故障效率提升 60%”，现场却说成“准确率 60 多”。建议下一轮明确拆开：

- 效率：例如平均单个工单初步排查耗时、每周人工投入工时或值班吞吐量；
- 质量：例如根因分类命中率、有效线索率或人工采纳率；
- 覆盖：多少工单进入 Agent 流程，其中多少具备足够日志与代码上下文。

如果目前只有效率数据，就不要主动声称准确率。

## 9. 反问环节偏“了解信息”，缺少展示岗位判断力的问题

**对应时间：约 38:51–43:50**

你问了工作节奏、业务内容、AI/全栈方向、团队规模和面试流程。这些问题都可以问，但排序和价值可以优化：

- 团队规模和面试轮次属于信息型问题，不能很好展示你对岗位的判断力。
- AI 和全栈方向与个人发展相关，比较好，但可以进一步关联岗位的实际挑战。

### 建议优先问

1. “这个岗位入职前三到六个月最希望解决的核心问题是什么？衡量做得好的标准是什么？”
2. “影音业务同时涉及硬件、App、Web 和 AI，当前前端在跨端协作中最大的技术难点是什么？”
3. “您刚才提到团队会往全栈发展，实际项目中前端最常承担到后端哪一层？团队会提供怎样的支持？”
4. “从您今天的面试感受看，我有哪些能力与岗位比较匹配，哪些地方还需要补充？”

工作节奏可以放到后面，更自然的问法是：

> “团队通常怎么安排版本节奏和值班机制？遇到硬件发布或大促节点时，工作节奏会有哪些变化？”

## 五、简历本身会触发但本场尚未深挖的问题

这些内容写在简历上，下一轮面试官很可能直接追问：

### 1. “具备全栈开发经验”

需要准备：NestJS 的模块与依赖注入、接口鉴权、异常处理、数据库事务、Redis 使用场景、缓存一致性，以及服务部署和可观测性。若目前主要是工具服务开发，建议口头表述为“具备 Node.js 服务端实践，能独立完成中小型前后端功能”，避免被按成熟后端工程师标准考察。

### 2. 协同编辑锁组件

“WebSocket + Redis 分布式锁保障数据一致性”是强声明。需要准备：锁粒度、获取与续租、超时、客户端断连、进程崩溃、锁误删、token/fencing、Redis 故障和最终一致性。单有分布式锁不等于保障数据一致性，最好说明它解决的是哪类并发编辑冲突。

### 3. Cocos 性能优化

需要准备：5 FPS 的测试设备和基线帧率、Draw Call 的采集工具、NodePool 对 GC/实例化的影响、图集合批的前提、纹理降位深带来的内存与画质权衡。

### 4. AI 教学应用生成平台

“生成 300+ 应用、2 小时缩短到 30 分钟”很亮眼，也会触发：生成成功率、人工修改比例、兼容性检测规则、模板和 Skill 如何约束模型、线上安全机制，以及你本人负责的边界。

### 5. Motiff 设计稿转代码

需要准备：为什么需要 FastMCP、Puppeteer 如何获取设计数据、所谓“原型链序列化限制”具体是什么、函数注入如何解决、JSON 压缩采用什么策略、55% 的基线和对生成质量是否有影响。

### 6. B 端性能监控

简历把 Long Task、FCP 和“核心交互耗时”放在一起，面试时要区分：FCP 是首次内容绘制指标，不等于交互耗时；交互响应更适合结合 Event Timing/INP、自定义业务埋点或 Performance API。还要准备 700ms 到 60ms 的具体瓶颈、算法复杂度变化和各项优化的独立贡献。

## 六、表达层面的共性问题

### 1. 填充词较多

音频中“呃”“然后”“其实”“可能”“我感觉”“对”出现频繁。它们会削弱技术结论的可信度，尤其是在面试官连续追问时。

建议使用固定三段式：

1. 一句话结论；
2. 两到三点机制或依据；
3. 一个真实项目例子和结果。

不知道时可以短暂停顿，然后说：

> “这个细节我需要区分一下已实现方案和理论方案。”

这比边想边说更稳。

### 2. 结论强度与证据不匹配

例如“肯定不会有副作用”“能够保证全局内存不会泄漏”等说法过强。工程方案通常只能在一定边界内提供保障。

建议改成：

- “在我们代理和记录的资源类型范围内，可以在卸载时清理”；
- “这降低了该类泄漏风险，但不能替代 heap 分析”；
- “实验中观察到该指标改善，线上因果还需要分段数据验证”。

### 3. 面试官纠正或质疑后，容易顺着对方说

技术面试不是一定要同意面试官。遇到不确定前提时，应先澄清：

> “如果您指的是删除 `<style>` 节点，我理解对应规则通常会失效；如果这里使用的是共享 stylesheet 或样式仍由其他节点注入，表现会不同。我们项目里具体是后一种/前一种情况。”

敢于礼貌澄清，反而体现技术判断力。

## 九、最终评价

你的核心竞争力是**做过真实、复杂且有业务指标的前端工程项目**。这场面试的主要问题不是经历不够，而是没有把经历转化为足够严谨、稳定、可经受连续追问的技术表达。
