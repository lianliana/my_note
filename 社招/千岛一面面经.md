## 一、整体感受

面试节奏较快，面试官主要根据自我介绍和项目经历向下追问，重点考查以下四块：

## 三、面试问题与复盘

### 1. 是否做过跨端开发？Hybrid 与小程序双线程架构有什么区别？

原回答要点：

- 做过 Hybrid 混合开发；
- Hybrid 由客户端提供原生能力，Web 实现通用业务逻辑和 UI；
- 微信小程序分为 UI / 渲染线程和 JS 逻辑线程；
- 小程序的 JS 运行环境由平台接管，API 和能力受到安全限制。

复盘：回答提到了安全与受控环境，但架构差异没有展开完整。

更完整的回答框架：

- Hybrid 通常以 WebView 为核心，JS 与 Native 通过 Bridge 通信，页面 DOM、样式计算和 JS 执行多在 WebView 环境中；
- 小程序通常将逻辑层和渲染层隔离：逻辑层运行 JS，渲染层负责视图，两侧通过序列化后的数据通信；
- 双线程除了安全隔离，还能限制开发者直接操作 DOM、统一渲染协议、提升平台的管控能力和多端一致性，并让逻辑执行与视图渲染在一定程度上解耦；
- 代价是跨线程通信、序列化和批量更新带来的额外开销。

### 2. 为什么小程序最后普遍采用双线程？除安全外还有什么收益？

原回答：现场思考较久，最后提到状态在 JS 侧更新，再驱动 UI 线程完成 State 到 View 的映射。

复盘：这是本场第一个明显卡顿点。建议用“目标—机制—收益—代价”回答：

1. 目标：安全、可控、跨平台一致；
2. 机制：逻辑层和渲染层隔离，通过平台定义的协议通信；
3. 收益：禁用不受控 DOM 能力、隔离阻塞、统一组件与渲染模型、便于审核和治理；
4. 代价：通信和序列化成本，频繁或大数据量更新会造成性能问题。

### 3. 为什么 `setData` 数据过大会卡顿？原生侧怎样拿到数据？

原回答要点：

- 存在线程间通信损耗；
- 可能有编码、解码开销；
- 用户操作、JS 状态更新、再下发 UI 绘制指令，会经历线程间流转。

面试官补充：**主要成本是序列化；两侧通信本质上类似 RPC，序列化占比较高。**

更完整的回答：

- `setData` 会将 JS 对象序列化，通过逻辑层与渲染层之间的通信通道传输，再在渲染侧反序列化；
- 数据量大时，序列化、拷贝、传输、反序列化都会占用时间和内存；
- 更新范围过大还会增加 diff、模板更新、布局和绘制成本；
- 高频调用会进一步堆积任务，挤占逻辑线程和渲染线程，造成掉帧；
- 优化方式包括只传变化字段、控制数据大小、合并高频更新、分页或虚拟列表、避免把纯业务数据放进视图状态。

### 4. 教学子应用生成平台中的 Agent 负责什么？个人负责哪部分？

#### 项目解决的用户问题

直播课中经常需要一些定制化的互动教学组件，例如答题游戏、实验演示、知识点动画或课堂互动工具。传统方式需要老师提出需求，再由产品、设计和研发排期开发，交付链路较长，而且一次性的长尾需求很难获得研发资源。

这个平台希望把开发过程产品化：老师不需要掌握前端工程，只需要通过自然语言描述课堂目标和交互形式，Agent 就能基于标准模板生成一个可运行、可预览，并且符合直播课接入规范的 Web App。

这里需要强调：它不只是让模型“写一段代码”，而是提供一个有模板约束、知识约束、运行环境和实时反馈的完整生成闭环。

#### Agent 在系统中负责什么

Agent 是连接老师需求与远端开发环境的执行中枢，主要承担以下职责：

1. **理解需求**：将老师的自然语言转化成页面、交互、素材和教学逻辑等可执行任务；
2. **读取约束**：通过 Skill 获得项目结构、组件用法、直播课协议、代码规范和验收要求；
3. **操作工程**：在隔离沙箱内读取、创建和修改文件，必要时安装依赖、执行构建或运行检查；
4. **验证结果**：启动项目，根据编译错误、运行日志或页面反馈继续修改；
5. **迭代交付**：把可访问的预览结果返回给老师，再根据后续对话持续调整。

因此，它更像一个工作在受控开发环境中的“前端开发 Agent”，而不是单轮的代码生成接口。

#### 端到端系统链路

一次完整的生成流程可以按以下方式讲：

1. 老师在前端聊天框输入需求，例如“生成一个适合小学数学课的分数配对游戏”；
2. 平台为当前任务创建或分配一个独立的 K8s 容器，准备好代码模板和运行环境；
3. Agent 加载系统提示、项目 Skill、老师需求及当前工程上下文；
4. Agent 通过文件和命令工具修改沙箱内的 Web App；
5. 沙箱启动开发服务器，平台将容器内端口通过受控网关暴露为预览地址；
6. 前端使用 iframe 加载预览页面，老师可以边对话边查看生成效果；
7. 如果编译或运行失败，Agent 读取错误信息并继续修复；如果老师提出修改，则在原工程和原会话上下文上增量迭代；
8. 生成结果通过校验后，进入保存、发布或接入直播课的后续流程。

可以将架构概括成：

`聊天交互层 → Agent 编排层 → Skill / Tool 层 → K8s 沙箱执行层 → 预览与发布层`

#### 模板与 Skill 分别解决什么问题

这两个概念要分开讲清楚：

- **Web App 模板约束工程起点**：预置目录结构、构建工具、基础组件、SDK、直播课运行协议和默认样式，避免 Agent 每次从空目录开始搭建；
- **Skill 约束 Agent 的工作方式**：告诉 Agent 应该如何理解项目、使用哪些组件与 API、按什么步骤修改、禁止做什么，以及完成后如何自检；
- 模板解决“生成出来的工程长什么样”，Skill 解决“Agent 应该怎样在这个工程里工作”；
- 两者结合，才能让生成结果从“看起来能运行”提升为“符合业务规范、可以接入现有体系”。

#### 个人负责的部分

可以将个人贡献归纳为三层，而不是简单罗列四项工作。

**1. 生成规范层：Web App 模板与 Skill**

- 设计 Agent 可稳定理解和修改的 Web App 模板；
- 将直播课接入规范、项目结构、组件使用方法和开发步骤沉淀到 Skill；
- 尽量减少模板中的隐式约定，让工程结构和命名本身能向 Agent 表达意图；
- 通过模板和 Skill 限制生成空间，降低错误依赖、错误目录和不兼容 API 等问题。

**2. 执行环境层：沙箱内项目生命周期**

- 负责在远端容器中准备项目、启动开发服务器并维护运行状态；
- 处理依赖安装、启动命令、端口配置和运行日志等工程问题；
- 让 Agent 修改代码后能够立即得到编译或运行反馈，形成“修改—执行—观察—修复”的闭环；
- 将每个任务限制在独立沙箱中，避免不同用户的代码、依赖和进程互相干扰。

**3. 预览链路层：容器到浏览器的实时访问**

- 将容器内开发服务器端口通过平台能力暴露给前端；
- 让前端通过 iframe 实时加载生成结果；
- 处理预览地址、路由、资源加载和容器生命周期之间的衔接；
- 目标是让老师不必下载、构建或部署代码，就能直接看到 Agent 的阶段性结果。

#### 回答时需要主动说明的职责边界

面试官问“这个 Agent 是几个人完成、你负责什么”，是在判断项目深度和个人贡献，不能把团队成果全部讲成自己的。建议明确区分：

- 自己直接负责：模板、Skill、沙箱内前端项目启动、端口暴露及预览链路；
- 自己参与联调：Agent 调用沙箱工具、错误反馈和生成流程；
- 如果没有直接负责，则不要声称负责：底层模型训练、通用 Agent Loop、K8s 集群基础设施、调度系统或完整发布平台。

可以这样表述：“完整平台由多名同学协作完成，我主要负责 Agent 能够稳定操作的前端工程环境，以及生成结果从沙箱到浏览器的预览链路。模型服务和通用 Agent 编排不是我从零实现的，但我参与了接口定义和联调，因此了解完整调用过程。”

#### 这个项目真正难的地方

**1. 生成稳定性，而不是首次生成成功**

大模型生成具有不确定性，可能修改错误文件、使用不存在的 API、引入不兼容依赖或只完成界面而遗漏业务协议。解决思路是通过模板收敛技术栈，通过 Skill 明确步骤和约束，再通过编译、Lint、测试或运行日志把错误反馈给 Agent。

**2. 长任务中的反馈闭环**

Agent 不能只生成代码就结束。它需要知道项目能否启动、页面是否可访问、控制台是否报错，并根据反馈继续修复。这要求命令执行结果、进程状态和日志能够结构化地返回给 Agent。

**3. 沙箱隔离和生命周期管理**

生成代码本质上是不可信代码，至少要考虑文件系统范围、命令权限、CPU / 内存、执行时间、网络访问和容器回收。即使这些不是个人直接负责，也应能说明为什么需要用隔离容器，而不是在公共服务上直接执行。

**4. 实时预览链路**

iframe 能否打开只是第一步，还要考虑开发服务器是否就绪、动态端口如何映射、静态资源路径、WebSocket / HMR 代理、跨域与 CSP、预览地址鉴权，以及容器停止后的失效处理。

**5. 业务规范注入**

通用模型并不知道公司内部组件、直播协议和课堂交互规范。与其把所有信息堆进一个超长 Prompt，更适合将稳定的操作规范沉淀为 Skill，把具体 API 文档按需检索，并在模板中直接预置高频能力。

#### 技术设计上的取舍

- **为什么使用远端 K8s 沙箱，而不是浏览器内运行？** 远端环境更接近真实 Node.js 工程，能够执行构建命令和管理依赖，也更便于做资源与权限隔离；代价是容器启动耗时、成本和调度复杂度更高。
- **为什么使用 iframe 预览？** iframe 能隔离生成页面与主站的样式和运行环境，接入简单；代价是需要处理跨域通信、尺寸同步、安全策略和预览地址鉴权。
- **为什么需要模板，而不是让 Agent 从零生成？** 从零生成自由度高但稳定性差，模板能统一工程规范、减少 Token 消耗并降低接入成本。
- **为什么用 Skill，而不是只写 System Prompt？** Skill 可以按任务加载、独立维护和版本化，也能把操作步骤与项目知识组织得更清晰；System Prompt 更适合放通用且始终生效的规则。

#### 业务结果怎样表达

录音里没有给出项目结果数据，正式面试前最好补齐真实指标，不能临时编造。优先准备以下数据：

- 老师从提出需求到得到首个可用版本，耗时从多少降到多少；
- 首次生成后能够成功启动或预览的比例；
- 平均需要几轮对话才能达到可用状态；
- 覆盖了多少类教学组件、多少老师或多少节课堂；
- 模板与 Skill 上线前后的编译失败率、人工修复率；
- 容器平均启动时间、预览成功率和任务完成耗时；
- 相比传统研发流程，节省了多少开发人力或排期时间。

如果暂时没有完整统计，可以诚实表达已验证的阶段性结果，例如：“项目当时仍处于探索阶段，还没有完整的业务规模数据；技术侧已经跑通从自然语言需求、沙箱改码到 iframe 实时预览的闭环。”

#### 推荐的 2 分钟面试回答

> 这个项目主要解决直播课里长尾互动组件的开发效率问题。过去老师提出一个互动需求，需要经过产品和研发排期；我们希望让老师直接用自然语言生成一个符合直播课规范的 Web App。
>
> 整体链路是：老师在聊天框描述需求，平台为任务准备一个独立的 K8s 沙箱，里面预置标准 Web App 模板。Agent 加载项目 Skill 后，通过文件和命令工具在沙箱里修改代码、启动项目，并根据编译或运行错误继续修复。容器内的开发服务会通过网关暴露成预览地址，前端再用 iframe 实时展示，所以老师可以一边对话一边调整应用。
>
> 完整平台由团队协作完成。我主要负责三部分：第一是 Web App 模板和 Skill，把项目结构、直播课协议、组件使用方式和自检步骤沉淀下来，收敛 Agent 的生成空间；第二是沙箱内前端项目的启动和运行反馈，让 Agent 修改后能马上得到编译结果；第三是容器端口到前端 iframe 的预览链路。
>
> 我认为这个项目的核心不是单次代码生成，而是生成稳定性和执行反馈闭环。模板负责给出稳定的工程起点，Skill 负责约束 Agent 的操作过程，沙箱负责安全执行，编译和预览结果再反馈给 Agent 继续迭代。最终我们跑通了从自然语言需求到可运行教学子应用的完整链路。业务结果方面，我还会补充真实的生成成功率、平均迭代轮数和交付耗时数据。

#### 本题复盘

项目形态与千岛岗位非常贴合：两者都涉及“面向开发者或业务用户的代码生成能力 + 标准工程规范 + Agent / Skill + 沙箱执行 + 平台接入”。原回答的问题不是没有内容，而是没有先建立系统全景，导致模板、K8s、Agent、Skill、端口和 iframe 混在一起。

下次应先用一句话说明用户价值，再用一条链路讲清系统，随后明确个人负责的三层工作，最后落到稳定性难点和真实指标。这样既能证明前端工程能力，也能自然引导面试官继续追问自己准备充分的 Agent 工程化部分。

### 5. Agent 的完整架构可以分为几层？

原回答要点：

- Agent 有主循环；
- 外挂 MCP、Skills 和 Tools；
- 每轮模型可能返回 Tool Use，调用工具获得更多上下文；
- 不再调用工具时退出循环。

复盘：说明理解 Agent Loop，但没有直接回答“分几层”。建议回答为：

1. **交互层**：用户输入、流式输出、会话管理；
2. **编排层**：任务拆解、Agent Loop、状态机、路由与终止条件；
3. **模型层**：提示词、模型调用、结构化输出；
4. **上下文 / 记忆层**：短期上下文、长期记忆、RAG；
5. **工具层**：Function Calling、MCP、Skills、外部 API；
6. **执行层**：沙箱、代码执行、文件系统和权限隔离；
7. **治理与可观测层**：重试、超时、预算、审计、Tracing、评测和安全策略。

具体项目不一定严格分成七层，但需要先给出清晰分层，再映射到项目实现。

### 6. Agent Loop 出现工具失败死循环时，如何避免？

场景：Agent 调用工具失败后不断重试同一工具。面试官指出，固定最大轮次会浪费很多无意义调用，而且不同复杂度任务不应统一设置最大轮次。

原回答：最大轮次兜底；工具连续失败时增加策略判断和兜底。

更好的回答：

- 为每次工具调用生成规范化指纹，识别“同工具 + 同参数 + 同错误”的重复模式；
- 设置按工具、错误类型划分的连续失败阈值，而非只依赖全局最大轮次；
- 对超时、限流等瞬时错误进行指数退避；对参数错误、权限错误等确定性错误禁止原样重试；
- 把失败原因结构化反馈给模型，要求修改参数、换工具或调整计划；
- 使用状态机 / 策略层决定 retry、replan、fallback、ask user 或 terminate；
- 最大步数、Token、耗时和费用预算仍作为最后防线，并根据任务复杂度动态分配；
- 记录轨迹和失败指标，通过离线评测持续优化循环策略。

### 7. 是否做过 RAG？怎样提高召回准确率？

原回答要点：

- 对输入和知识内容做向量化；
- 优化切片策略，避免关键上下文被不合理拆散；
- 结合向量召回和更适合型号、技术关键词的检索方式；
- 多路召回后进行粗排、精排。

复盘：方向基本正确，但术语表达不够稳定。建议标准化为：

- 文档解析与元数据清洗；
- 按语义、标题层级或代码结构 Chunk，并设置合理重叠；
- Query Rewrite / Query Expansion；
- Dense Retrieval + BM25 稀疏检索的 Hybrid Search；
- 多路召回结果融合（如 RRF）；
- Cross-Encoder / LLM Rerank；
- 元数据过滤、权限过滤和时间过滤；
- 通过 Recall@K、MRR、NDCG 及端到端答案正确率做评测。

### 8. 项目用了 RAG 检索层还是 Agent Search？

原回答：使用 Agent Search，让 Agent 直接调用知识库暴露的 HTTP 接口。

复盘：最好补充为什么这么选、接口返回什么、是否有重排、搜索失败如何降级，以及这与传统 RAG Pipeline 的边界。

### 9. 对话通信为什么用 SSE？SSE 和 WebSocket 各适合什么场景？

原回答要点：

- 项目使用 SSE；
- WebSocket 是全双工通信，需要维持长连接和心跳，客户端、服务端都能主动发送消息；
- SSE 是客户端发起请求、服务端持续推送，适合 AI 对话的流式返回，成本相对较低。

更完整的对比：

| 维度 | SSE | WebSocket |
| --- | --- | --- |
| 通信方向 | 服务端到客户端单向推送 | 全双工 |
| 协议 | 基于 HTTP，文本事件流 | HTTP Upgrade 后使用 WebSocket 帧 |
| 断线恢复 | 浏览器原生支持重连及 `Last-Event-ID` | 通常自行实现 |
| 适用场景 | LLM 流式输出、通知、日志 | 聊天、协同编辑、游戏、实时双向控制 |
| 数据类型 | 以文本为主 | 文本和二进制 |

AI 对话通常是“一次请求、持续响应”，因此 SSE 简单且契合；如果需要服务端主动发起复杂交互或高频双向通信，则更适合 WebSocket。

### 10. 是否做过服务端开发？数据库索引一般怎么建？

原回答：根据线上慢查询判断是否命中索引，再针对性建立联合索引。

复盘：回答偏事后处理。更好的框架是：

- 先根据高频查询模式设计索引，而不是只等慢查询出现；
- 联合索引结合过滤、连接、排序、分组字段设计，遵守最左前缀原则；
- 高选择性字段通常更适合作为索引前部，但同时要结合范围查询和排序需求；
- 使用 `EXPLAIN` / `EXPLAIN ANALYZE` 验证执行计划；
- 权衡写放大、存储空间与索引维护成本，避免重复和低收益索引。

### 11. 如何防止慢查询？

原回答：使用索引、Redis 缓存、读写分离，数据量很大时分库分表。

复盘：方向没错，但回答直接跳到了重型方案。建议按成本从低到高回答：

1. 建立监控：慢查询日志、P95/P99、扫描行数、锁等待；
2. 优化 SQL：避免 `SELECT *`、控制返回量、批量查询、避免 N+1；
3. 优化索引并用执行计划验证；
4. 控制深分页，必要时使用游标分页；
5. 对热点读使用带一致性与失效策略的缓存；
6. 处理锁竞争和长事务；
7. 最后再考虑读写分离、分区、分库分表等架构方案。
